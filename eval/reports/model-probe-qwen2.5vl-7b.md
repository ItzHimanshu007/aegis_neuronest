## JSON mode: `json_object` vs `json_schema`

This report is the `json_object` run (`AEGIS_LLM_JSON_MODE=json_object`, `server/.env`'s default).
A second run against the same fixtures with `AEGIS_LLM_JSON_MODE=json_schema` measured lower
schema validity and grounding for this model — 6/10 schema-valid and 3/5 first-action grounding,
against 7/10 and 7/7 here — so `json_object` is the more reliable mode for qwen2.5vl:7b on this
pipeline. Full per-fixture numbers:
[`model-probe-qwen2.5vl-7b-json-schema.md`](model-probe-qwen2.5vl-7b-json-schema.md).

## Candidate comparison: qwen3-vl:4b

Measured 2026-09-18 against the same 10 fixtures, same conditions (`json_object`, prompt `3b.1`,
SoM on): **2/10 schema-valid (20%)**, **2/10 JSON-valid first try (20%)**, p50 latency **132041 ms**
— worse on every axis than qwen2.5vl:7b above, not meaningfully better, and markedly slower (it is
the smaller of the two models by parameter count, which does not carry over into reliability on
this pipeline). It fails mostly with `MODEL_OUTPUT_INVALID` (schema violations surviving the one
repair pass), not `MODEL_OUTPUT_UNGROUNDED` — when its output does parse, grounding is 2/2. Full
numbers: [`model-probe-qwen3-vl-4b.md`](model-probe-qwen3-vl-4b.md). qwen2.5vl:7b remains the
default; this candidate is not adopted.

## Conditions and limits

- Fixtures are sealed payloads from `demo-portal`, generated by `extension/e2e/probe-fixtures.spec.ts`. They are authored pages, not a held-out set: Stage 4 owns generalization.
- Grounding is scored on the FIRST action only, against one gold element per fixture.
- Latency is measured from this machine, including network time to the endpoint.
